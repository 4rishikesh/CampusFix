# CampusFix

**A Smart, Secure Campus Lost & Found Platform for NIT Warangal**

CampusFix is a full-stack web application designed to simplify the process of reporting, discovering, and recovering lost belongings within a campus community. It provides a centralized platform where students and faculty can report lost or found items, discover potential matches, communicate securely, and receive relevant updates.

Built using **React, Node.js, Express, and MongoDB**, CampusFix combines intelligent item matching, secure authentication, privacy-focused reporting, and administrator moderation to create a reliable campus lost-and-found ecosystem.

---

## Key Features

### 1. Authentication & User Management
- Secure user registration and login using JSON Web Tokens (JWT).
- Protected routes and authenticated profile access.
- NIT Warangal email-domain validation for new public registrations.
- Role-based access control for ordinary users and administrators.
- Database-backed authorization for administrative operations.

### 2. Lost & Found Management
- Create and manage lost-item reports.
- Publish lost reports publicly or keep them private.  
- Submit found-item reports with private-by-default visibility.
- Update, archive, and delete reports.
- View and manage personal reports through the user dashboard.
- Secure image uploads for item identification.

### 3. Intelligent Item Matching Engine

CampusFix includes a deterministic matching engine that compares active lost and found reports to identify potential matches.

**Matching techniques:**
- Natural Language Processing (NLP) text normalization.
- Porter Stemming for word normalization.
- Jaro-Winkler similarity for typo-tolerant text comparison.
- 64-bit Discrete Cosine Transform (DCT) perceptual image hashing.
- Persistent and idempotent lost/found match records.

The matching engine helps users discover potential leads based on item descriptions and images. A generated match is an indication of similarity, not proof of ownership.

### 4. Secure Communication & Notifications
- Secure communication between relevant users.
- Notifications for relevant application activities and updates.
- Integrated communication workflow to help users coordinate item recovery.

### 5. User Dashboard
- View and manage personal lost and found reports.
- Track report status.
- View potential matches generated by the matching engine.
- Access relevant application updates and notifications.

### 6. Administrator Dashboard
- Dedicated, protected `/admin` dashboard.
- View and manage registered users.
- Block and unblock user accounts.
- Review private reports through authorized administrative access.
- Moderate reports and manage held submissions.
- Database-backed administrator authorization.

### 7. Image Upload & Processing
- Image uploads through Multer and Cloudinary.
- Server-side file validation.
- Supported formats: JPEG, PNG, and WebP.
- Maximum upload size: 5 MB.
- Image processing and perceptual hashing for matching.

### 8. Security & Reliability
- JWT-based authentication.
- Server-side ownership and authorization checks.
- Private-by-default found reports.
- Protected administrative endpoints.
- Helmet security headers.
- API rate limiting.
- Configurable CORS.
- Backend-controlled validation of sensitive report fields.
- Database-backed user blocking and moderation.

## Application Architecture

CampusFix follows a client-server architecture.

1. **Frontend:** React provides the user interface for authentication, reporting, dashboards, matching, and communication.
2. **Backend:** Express.js handles API requests, authentication, business logic, authorization, and report management.
3. **Database:** MongoDB stores user accounts, reports, match records, and application data.
4. **Image Storage:** Cloudinary handles uploaded item images.
5. **Matching Engine:** Processes eligible lost and found reports using text and image similarity techniques.
6. **Administration:** Protected backend APIs enforce administrator permissions and moderation rules.

## Getting Started

### Prerequisites

Make sure you have the following installed:

- Node.js 18 or later
- npm
- MongoDB (local or hosted)
- Cloudinary account for image uploads

### 1. Clone the Repository

```bash
git clone https://github.com/4rishikesh/CampusFix.git
cd CampusFix
```

### 2. Backend Configuration

Create a `.env` file inside the `backend` directory.

```env
PORT=5000
MONGO_URI=mongodb://127.0.0.1:27017/campusfix_dev
JWT_SECRET=your_long_random_secret
CLIENT_ORIGIN=http://localhost:5173

ADMIN_BOOTSTRAP_EMAIL=campus-admin@example.edu

CLOUDINARY_CLOUD_NAME=your_cloud_name
CLOUDINARY_API_KEY=your_api_key
CLOUDINARY_API_SECRET=your_api_secret
```

Cloudinary credentials are available under:

**Cloudinary Console → Dashboard → Product Environment Credentials**

All three Cloudinary variables are required for image uploads. Reports without images can still be created without Cloudinary configuration.

### 3. Frontend Configuration

Create `src/.env` from `src/.env.example` if you need to configure a custom backend URL.

```env
VITE_API_BASE_URL=http://localhost:5000
```

Only frontend-safe configuration belongs in this file. Never expose backend credentials through frontend environment variables.

### 4. Install Backend Dependencies

Open a terminal:

```bash
cd backend
npm install
npm start
```

The backend API will run at:

`http://localhost:5000`

### 5. Install Frontend Dependencies

Open another terminal:

```bash
cd src
npm install
npm run dev
```

Vite will display the frontend URL, normally:

`http://localhost:5173`

## Administrator Setup

Administrator privileges are assigned through a controlled bootstrap process.

1. Register the account that should become the administrator.
2. Set `ADMIN_BOOTSTRAP_EMAIL` in `backend/.env` to the exact registered email address.
3. Execute the seed command:

```bash
cd backend
npm run seed:admin
```

The seed script:
- Requires a valid MongoDB connection.
- Refuses to promote an account that does not exist.
- Refuses to promote blocked accounts.
- Is executed manually and is not automatically run when the server starts.

Administrators use the regular login page and are redirected to the protected `/admin` dashboard.

---

## Registration Rules

New public accounts must use valid NIT Warangal email addresses.

**Supported domains:**

- Students: `name@student.nitw.ac.in`
- Faculty/Staff: `name@nitw.ac.in`

Email validation includes whitespace normalization, casing normalization, and exact domain validation.

Gmail addresses, lookalike domains, and subdomains are rejected.

Faculty and staff accounts are created as ordinary users. An email domain does not automatically grant administrator privileges.

## API Overview

All protected endpoints require a valid JWT bearer token.

### Lost & Found APIs

| Method | Endpoint | Description |
|---|---|---|
| POST | `/api/items/lost` | Create a lost-item report |
| POST | `/api/items/found` | Create a found-item report |
| GET | `/api/items/lost` | Retrieve public active lost reports |
| GET | `/api/items/my-items` | Retrieve personal reports |
| GET | `/api/items/my-matches` | Retrieve potential matches |
| GET | `/api/items/:id` | Retrieve an authorized report |
| PUT | `/api/items/:id` | Update a report |
| PATCH | `/api/items/:id/archive` | Archive a report |
| DELETE | `/api/items/:id` | Delete a report |

The public lost-report endpoint supports pagination and filtering:

```text
GET /api/items/lost?page=1&limit=20&category=&search=
```

Lost and found creation endpoints accept multipart form data with an optional `image` field.

### Administrator APIs

| Method | Endpoint | Description |
|---|---|---|
| GET | `/api/admin/users` | Retrieve users |
| PATCH | `/api/admin/users/:id/block` | Block a user |
| PATCH | `/api/admin/users/:id/unblock` | Unblock a user |
| GET | `/api/admin/items` | Retrieve reports for moderation |
| PATCH | `/api/admin/items/:id/moderation` | Moderate a report |

All administrator endpoints require database-authorized administrator access.

For complete endpoint specifications, refer to [API Documentation](docs/API.md).

## Privacy & Moderation

CampusFix enforces report visibility and access permissions at the backend level.

- Lost reports can be public or private.
- Found reports are always private.
- Found reports never appear in the public community feed.
- Found-report details are accessible only to their owners and authorized administrators.
- Sensitive fields such as `visibility`, `type`, `user`, and `imageHash` cannot be manipulated through crafted client requests.
- Blocked users cannot access protected report operations.
- Active reports belonging to blocked users are held for administrator review and excluded from public listings and matching.
- Unblocking does not automatically republish held reports. An administrator must explicitly release or archive them.

These controls ensure that privacy and authorization are enforced independently of frontend behavior.
